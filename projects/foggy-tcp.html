User-Space TCP Implementation

Fall 2025 · ELEC 3120 Computer Networks

I implemented Foggy TCP for ELEC 3120, a TCP socket that runs in user space. An application sends and receives through the socket, and a backend thread carries each segment in a UDP datagram. The course testbed is two virtual machines, a server at 10.0.1.1 and a client at 10.0.1.2, on a link of 100 Mbps with 20 ms of delay.

Measuring delivery delay

I measured how long a file takes to cross the link, from the client’s first write until the server has the whole file. The client writes the file into the socket, and the server stores what it reads.

The start time travels in the byte stream. Just before the first write, the client stamps the clock and prefixes the stamp to the data. The server removes it, writes the remaining bytes as the file, and stamps the clock again when the read returns empty. The printed difference is the delivery time. The socket closes only after the end stamp, so setup and teardown stay outside the measurement.

Sliding window

I replaced stop-and-wait with a sliding window, so several segments can be in flight. Stop-and-wait sent one segment and then waited for its acknowledgement.

The sender numbers the byte stream and breaks it into segments of at most one MSS. The window holds every segment the receiver has not yet acknowledged, and the sender transmits each one it has not yet sent. The receiver acknowledges the next byte it still expects, and that acknowledgement covers every earlier byte. When the acknowledgement advances, the sender releases the covered prefix and the window slides forward.

Segments that arrive out of order stay in a buffer. A segment that jumps ahead of a gap is stored, and bytes reach the application only once they continue from the next expected offset. The buffer has 64 slots. A segment that has already been delivered or stored is dropped. An MSS is 1,400 bytes minus the Foggy header.

Fast retransmit and Reno

I used fast retransmit for loss recovery, so a loss does not wait for a timeout. Three duplicate acknowledgements of the same next byte mean the segment at that sequence number was lost, and the sender retransmits it immediately.

I capped unacknowledged data by the smaller of the receiver’s advertised window and a congestion window. The congestion window follows Reno.

Reno begins in slow start. The window is one MSS, and the slow-start threshold is 64 MSS. Each acknowledgement of new data adds one MSS, so the window roughly doubles over a round trip. At the threshold the sender enters congestion avoidance, where the window grows by about one MSS per round trip. On a loss the threshold falls to half the current window, the window becomes that threshold plus three MSS, and the sender enters fast recovery. The next acknowledgement of new data leaves recovery: the window returns to the threshold, and congestion avoidance continues.

The cap counts payload bytes sent but not yet acknowledged. Another segment goes out only when it still fits. The receiver advertises the free space in a 65,535-byte buffer, or one MSS when less space remains.

TCP CUBIC

Reno opens the window by about one segment per round trip, which is slow on a wide pipe. For the last stage I kept slow start and fast retransmit, and switched congestion avoidance and the loss decrease to TCP CUBIC.

On a loss the sender saves the current window as Wmax and multiplies the window by β = 0.7. In congestion avoidance the target follows the time since the loss, rather than the number of round trips:

W(t) = C (t − K)³ + W_max
K    = ∛(W_max · β / C)

C is 0.4, and t is the time in seconds since the reduction. When the target is above the current window, each new acknowledgement moves the window toward it.

The slow-start threshold is set to this reduced window at the same time. During fast recovery, each further duplicate acknowledgement grows the window by one MSS, so the window can still advance while the loss is repaired. An acknowledgement of new data ends fast recovery: the window returns to the threshold, and congestion avoidance resumes. Each step toward the target grows the window by (W(t) − cwnd) · MSS / cwnd bytes, or by one byte when that increase would be smaller.
