Amy compiler

Spring 2026 · COMP 4121 Modern Compiler Construction

Amy is the teaching language for COMP 4121. It is a small fragment of Scala. A program is a module. Functions are expressions, and the language has no separate statement form: a conditional returns a value, and ; sequences two expressions, discarding the value of the first. User-defined types are algebraic data types, an abstract class with case-class constructors, and match decomposes a value by constructor. The language specification defines the grammar. The pipeline below is the implementation.

An interpreter and a WebAssembly compiler consume the same typed tree. They share the front end through type checking.

source
  lexer           longest-match tokens
  parser          an LL(1) tree
  name analysis   every use resolved
  type checking   constraints, then unification
                    ├─ interpreter
                    └─ WebAssembly

Regex-based lexing

The lexer is a set of regular patterns for identifiers, integer literals, string literals, operators, and comments. When several patterns match at the same position, the longest match is selected. An identifier that spells a reserved word is classified as that keyword. Line comments run from // to the end of the line. Block comments run from /* to */ and do not nest, so a second /* inside a comment is ordinary text. Escape sequences in string literals are not interpreted: a backslash followed by n is those two characters. Input that matches no pattern is a lexical error.

LL(1) parsing

The parser is LL(1): one token of lookahead selects the next production. Operator precedence is fixed, so multiplication groups more tightly than addition, and every binary operator except sequencing associates to the left. The right-hand side of a val binding ends at the first semicolon, while the bound name remains visible through the semicolons that follow. A match expression is rejected as the left operand of an arithmetic operator.

Name analysis

Amy has no import. A name defined in another module is written in qualified form, as in Std.printString. Name analysis checks that every use resolves and that two definitions in the same scope do not share a name. A local val may shadow a parameter. A definition may be used before it appears in the file, so resolution is over the whole module.

Constraint-based type checking via unification

The built-in types are 32-bit integers, strings, booleans, and Unit, the type of an expression evaluated only for its effect. The checker walks the tree and emits a constraint wherever two types must agree: the two branches of a conditional, a call and its definition, and a pattern and the value it matches. Unification solves the constraint set. A program whose branches disagree, or whose call has the wrong number of arguments, is rejected here and is not passed to either back end.

Interpretation and WebAssembly generation

The interpreter evaluates the typed tree directly. A value is a 32-bit integer, a boolean, a string, unit, or a case class, represented as a constructor name and the values of its arguments. The standard library is implemented in the host language: printInt, printString, readString, and readInt. Integers and booleans are compared by value. Strings and case classes are compared by reference. Sequencing evaluates both expressions and returns the second. A val extends the local environment for its body. A conditional returns the value of the selected branch. A constructor call builds a case-class value. A call to an ordinary function evaluates the function body under the argument values.

The compiler lowers the same tree to WebAssembly, including the standard library for printing and reading. A program that passes type checking can therefore be executed by either back end.
