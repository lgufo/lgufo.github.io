Indirect-call program generation

Fall 2025 · With Ivan Lok and Puyang Zhang · Supervised by Prof. Jiasi Shen, with Ph.D. student Huiri Tan

A model that turns WebAssembly back into readable C++ has a particular blind spot. In the binary, a call through a function pointer is an indirect jump through a table. The function’s name, and the reason the program picked it, are gone. To teach a model to recover that, we wanted many C++ programs in which function pointers and indirect calls appear often, in different shapes, and we wanted each program to compile. Ivan Lok, Puyang Zhang, and I tried two ways to get those programs.

Rewrite programs that already exist

Human-written code is already varied, so we started there: CodeNet, The Stack, and a smaller set of less famous repositories. Files were kept under a thousand lines and split when they were longer. A model was asked, with a few handwritten examples, to rewrite each program so it would lean on C-style function pointers while keeping the original behavior. A script then compiled the result and, on failure, sent the compiler errors back for a repair.

The accepted programs did contain indirect calls. Many of them fought the source they came from. A straight-line algorithm, or code built around C++ resource management, has little natural use for a callback, so the pointer often looked pasted on. Lengths also piled up around 90–130 lines. The model kept deleting parts it judged unnecessary, so a long input and a short input came out a similar size.

Build a skeleton, scramble it, ask for a reconstruction

The second pipeline decides the shape before the model writes anything. A Python generator, using templates, picks four or five patterns from a library of about fourteen. The library is aimed at things a decompiler finds hard: an array of function pointers, a struct that holds one, a state machine driven by a map, nested structures, and a chain of callbacks. The generator emits a compilable outline, with its own random names, sizes, and thresholds.

We then damage that outline on purpose. Blocks of ten to twenty lines are shuffled. Function bodies are deleted while the signatures stay. Statements are cut in half. A misleading fragment is dropped in. The model has to reconstruct a program that still respects the names and pieces left behind. A memorized example does not fit, because the skeleton is different every time.

A repair loop compiles the reconstruction with Clang, for native code and for WebAssembly, and feeds the errors back for at most two more tries. Each accepted program is stored with a JSON file: which patterns were requested, the random parameters, how many repairs it took, and the control-flow signature we expect, such as the size of a function-pointer table. That file is the ground truth for a later benchmark. A decompiler is scored on whether it recovered those patterns, not on whether its text matches ours.

On a pilot of 300 programs, raw reconstructions compiled about 60% of the time. After the repair loop, all 300 compiled for both targets. They landed around 250–350 lines, and every sample used at least four distinct kinds of indirect control flow.

What we got Indirect calls were present, often looking pasted on. Length stuck around 90–130 lines. 300 of 300 compiled after repair, at about 250–350 lines, with several indirect-call patterns in each.

The second pipeline was the one we would actually use for a dataset. The rewrite path had seemed promising because the source was already diverse. The skeleton made that diversity something we could request.
