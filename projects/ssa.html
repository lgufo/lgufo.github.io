LLVM SSA construction

Summer 2025 · Supervised by Prof. Jiasi Shen, with Ph.D. student Huiri Tan

The pass takes LLVM IR in which a variable may be assigned more than once and rewrites it so that each assignment has a distinct name. A use then refers to exactly one definition, including across branches and loops. The construction follows Cytron’s algorithm as presented in Cooper and Torczon’s Engineering a Compiler: a dominance tree, phi functions on the dominance frontier, and a renaming walk. The pass was the first component of a UROP on compiler autotuning.

Setup

Before the SSA pass, I completed LLVM’s Kaleidoscope tutorial, covering lexing, parsing, the abstract syntax tree, code generation, and control flow. I then implemented an analysis pass that reports, for each function, the number of basic blocks, the number of instructions, the maximum loop-nesting depth, and the operand types. The surrounding work was building LLVM with CMake and Ninja, registering the pass, and traversing the IR.

Dominance

Block A dominates block B when every path from the function entry to B passes through A. The immediate dominator of B is the closest such block, and the immediate-dominator relation forms a tree. Later steps walk that tree. I computed dominance sets by fixed-point iteration in reverse postorder. For every block other than the entry, the immediate dominator is the member of its dominance set, excluding the block itself, that dominates no other member of the set.

Dom(entry) = { entry }
for each other block b:
    Dom(b) = all blocks
repeat until nothing changes:
    for each block b in reverse postorder, except entry:
        Dom(b) = { b } ∪ intersection of Dom(p)
                 over predecessors p of b
for each block b except entry:
    idom(b) = the member of Dom(b), other than b,
              that dominates no other member

Phi placement

At a control-flow join, incoming paths may carry different values of the same variable. SSA represents that choice with a phi instruction at the start of the block. The algorithm inserts a phi only on the dominance frontier of a definition: the first blocks that the definition does not dominate, where the new value becomes visible along more than one path. A phi is itself a definition, so the frontier of its block may require a further phi.

for each variable v:
    assigned = blocks that write v
    worklist = assigned
    while worklist is not empty:
        b = pop(worklist)
        for each block f in the dominance frontier of b:
            if f has no phi for v:
                insert phi(v) at the top of f
                if f is not in assigned:
                    add f to assigned and to worklist

Renaming

Renaming walks the dominator tree and maintains a stack of names for each original variable. In a block, each assignment pushes a fresh name, and each use is rewritten to the name on top of its stack. The current names fill the phi operands of successor blocks for the outgoing edge. On return from the block, those names are popped, so a sibling in the dominator tree again sees the names defined in the parent.

rename(b):
    pushed = empty
    for each phi in b:
        push a fresh name for the phi’s variable
        record that push in pushed
    for each ordinary instruction I in b:
        rewrite each use to the name on top of its stack
        if I writes v:
            push a fresh name for v
            record that push in pushed
    for each successor s of b:
        fill the phi operands in s for the edge b → s
        from the names currently on top of the stacks
    for each child c of b in the dominator tree:
        rename(c)
    pop every name recorded in pushed

Example: conditional join

The first example writes one stack slot on both sides of a branch and loads it after the join. Both paths overwrite the value stored in the entry, so the pass removes the slot. The value that reaches the return is a phi. Highlighted instructions are the stack operations the pass removes and the phi that replaces them.

define i32 @test(i32 %cond) {
entry:
  %x = alloca i32
  store i32 1, i32* %x
  %cmp = icmp eq i32 %cond, 0
  br i1 %cmp, label %then, label %else

then:
  store i32 2, i32* %x
  br label %end

else:
  store i32 3, i32* %x
  br label %end

end:
  %y = load i32, i32* %x
  ret i32 %y
}
define i32 @test(i32 %cond) {
entry:
  %cmp = icmp eq i32 %cond, 0
  br i1 %cmp, label %then, label %else

then:                                ; preds = %entry
  br label %end

else:                                ; preds = %entry
  br label %end

end:                                 ; preds = %else, %then
  %x0 = phi i32 [ 3, %else ], [ 2, %then ]
  ret i32 %x0
}

Example: loop with a side path

The second example keeps two stack slots live across a loop. The loop body updates one of them, and a side path multiplies the two values and stores the product before the next iteration. After the pass, each slot is a phi at the loop header and at the join inside the body. Highlighted instructions are the removed stack operations and the phis and uses that replace them. The loop index was already in SSA, so the pass leaves it unchanged.

After

define i32 @complex(i32 %a, i32 %b, i32 %n) {
entry:
  %x = alloca i32
  %y = alloca i32
  store i32 %a, i32* %x
  store i32 %b, i32* %y
  br label %loop

loop:
  %i = phi i32 [ 0, %entry ], [ %i.next, %merge ]
  %cond1 = icmp slt i32 %i, %n
  br i1 %cond1, label %body, label %exit

body:
  %tmp1 = load i32, i32* %x
  %tmp2 = load i32, i32* %y
  %cond2 = icmp sgt i32 %tmp1, %tmp2
  br i1 %cond2, label %then, label %else

then:
  %add = add i32 %tmp1, 1
  store i32 %add, i32* %x
  br label %merge

else:
  %sub = sub i32 %tmp2, 1
  store i32 %sub, i32* %y
  br label %merge

merge:
  %i.next = add i32 %i, 1
  %cond3 = icmp eq i32 %i.next, 5
  br i1 %cond3, label %special, label %loop

special:
  %tmp3 = load i32, i32* %x
  %tmp4 = load i32, i32* %y
  %mul = mul i32 %tmp3, %tmp4
  store i32 %mul, i32* %x
  br label %loop

exit:
  %result = load i32, i32* %x
  ret i32 %result
}
define i32 @complex(i32 %a, i32 %b, i32 %n) {
entry:
  br label %loop

loop:                                ; preds = %special, %merge, %entry
  %y0 = phi i32 [ %y1, %special ], [ %y1, %merge ], [ %b, %entry ]
  %x0 = phi i32 [ %mul, %special ], [ %x1, %merge ], [ %a, %entry ]
  %i = phi i32 [ 0, %entry ], [ %i.next, %merge ]
  %cond1 = icmp slt i32 %i, %n
  br i1 %cond1, label %body, label %exit

body:                                ; preds = %loop
  %cond2 = icmp sgt i32 %x0, %y0
  br i1 %cond2, label %then, label %else

then:                                ; preds = %body
  %add = add i32 %x0, 1
  br label %merge

else:                                ; preds = %body
  %sub = sub i32 %y0, 1
  br label %merge

merge:                               ; preds = %else, %then
  %y1 = phi i32 [ %sub, %else ], [ %y0, %then ]
  %x1 = phi i32 [ %x0, %else ], [ %add, %then ]
  %i.next = add i32 %i, 1
  %cond3 = icmp eq i32 %i.next, 5
  br i1 %cond3, label %special, label %loop

special:                             ; preds = %merge
  %mul = mul i32 %x1, %y1
  br label %loop

exit:                                ; preds = %loop
  ret i32 %x0
}

These two functions were the test cases. In the branch, the two stores of one slot become the operands of a single phi, and the slot is removed. In the loop, each slot live across a back edge becomes a phi at the header, and the join inside the body receives a phi of its own.
