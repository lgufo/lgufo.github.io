Indirect-call program generation

Fall 2025 · With Ivan Lok and Puyang Zhang · Supervised by Prof. Jiasi Shen, with Ph.D. student Huiri Tan

Recovering C++ from WebAssembly requires reconstructing indirect calls. In the binary, a call through a function pointer is call_indirect, an indirect jump through a table. The callee’s name and the reason it was selected are absent. Training a model to recover them requires many compilable C++ programs in which function pointers and indirect calls appear in varied forms.

A direct prompt to write such a program does not produce that set. Outputs collapse onto a few recurring patterns, principally calculators and sorting comparators. With Ivan Lok and Puyang Zhang, we compared two generation pipelines for compilable programs with greater structural variety.

Dataset transformation

The first pipeline rewrites existing programs. We used three sources: CodeNet, on the order of 500,000 C++ solutions to programming problems; The Stack, a large collection of permissively licensed GitHub code; and Wild-C, an internal set of about 120,000 translation units from lesser-known repositories. Files longer than 1,000 lines were split.

A gpt-4o prompt, with a few handwritten examples, instructed the model to rewrite each program so that it used C-style function pointers while preserving the original behavior. A script compiled the result and, on failure, returned the compiler diagnostics for repair.

The accepted programs contained indirect calls. Many rewrites fit the source poorly. Straight-line algorithms and code organized around C++ resource management have little use for a callback, so the inserted pointer was often incidental to the computation. Output length concentrated around 90–130 lines. The model deleted material it treated as unnecessary, and long and short inputs produced outputs of similar size.

Skeleton generation and reconstruction

The second pipeline fixes the program shape before the model writes code. A Python generator, using Jinja2 templates, selects four or five patterns from a library of fourteen. The library targets constructs that are difficult for a decompiler: an array of function pointers, a struct that holds a function pointer, a state machine driven by a map, nested structures, and a chain of callbacks. The generator emits a compilable outline with randomized names, sizes, and thresholds.

We then degrade that outline. Blocks of ten to twenty lines are shuffled. Function bodies are deleted and signatures are retained. Statements are truncated. A misleading fragment is inserted. The model must reconstruct a program consistent with the remaining names and fragments. Because the skeleton changes on every sample, a memorized example cannot satisfy the prompt.

A repair loop compiles the reconstruction with Clang, for native x86-64 and for wasm32-wasi, and returns the diagnostics for at most two further attempts. Each accepted program is stored with a JSON record for later benchmarking: the requested templates, the random parameters (seeds, array sizes, and thresholds), the repair record (attempts, token use, and binary size), and the expected control-flow signature, including function-pointer table size and call depth. A decompiler is scored on whether it recovered those patterns.

On a pilot of 300 programs, raw reconstructions compiled about 60% of the time. After the repair loop, all 300 compiled for both targets. Programs were about 250–350 lines, and every sample contained at least four distinct forms of indirect control flow.

Method gpt-4o few-shot rewrite of CodeNet, The Stack, and Wild-C, followed by compile-and-repair Jinja2 skeleton, structural noise, then reconstruction with at most two Clang repairs
Result Indirect calls were present, often incidental to the original computation. Length concentrated around 90–130 lines. 300 of 300 programs compiled for native code and WebAssembly, at about 250–350 lines, with at least four indirect-call patterns in each.

We adopted the second pipeline for dataset construction. Its noise remains mostly syntactic: names change and blocks move, while the underlying template stays similar. A later version would mutate the abstract syntax tree and check that the generated pointers are reached during execution.
