Amy compiler

Spring 2026 · COMP 4121 Modern Compiler Construction

Amy is the teaching language for COMP 4121. It sits close to a small slice of Scala. A program is a module. Functions are expressions, and there is no separate statement form: a conditional returns a value, and ; sequences two expressions by discarding the first. User-defined types are algebraic data types, an abstract class plus case-class constructors, and match takes a value apart by which constructor built it. The language specification is the reference for the grammar. What follows is the pipeline I implemented, not that document.

I built two ways to run a program. An interpreter walks the tree and produces the answer. A compiler lowers the same tree to WebAssembly. They share the front end.

Regex-based lexing

The lexer is a set of regular patterns: identifiers, integer literals, string literals, operators, and comments. A longest match decides which pattern wins when several could start at the same character. An identifier that spells a reserved word is that keyword, not a name. Line comments run from // to the end of the line. Block comments run from /* to */ and do not nest, so a second /* inside one is ordinary text. The string rule is the part people miss: escapes are not interpreted. The characters backslash and n inside quotes are those two characters, not a newline.

LL(1) parsing

One token of lookahead is enough to choose the next grammar production, which is what LL(1) means here. The interesting constraints are the ones the raw grammar over-approximates. Operators have a fixed precedence, so multiplication groups tighter than addition, and every binary operator except sequencing associates to the left. A val binding’s right-hand side stops at the first semicolon, while the name stays visible through the semicolons that follow. match cannot sit in the left operand of an arithmetic operator. The parser rejects those shapes even though a careless grammar would accept them.

Name analysis

Amy has no import. A name in another module is written out in full, as Std.printString. Name analysis checks that every use resolves, that two definitions in the same scope do not share a name, and that a local val may shadow a parameter. Definitions may be used before they appear in the file.

Constraint-based type checking via unification

The built-in types are 32-bit integers, strings, booleans, and Unit, the type of a computation that is only there for its effect. The checker walks the tree, emits a constraint wherever two types must agree (both branches of a conditional, a call and its definition, a pattern and the value it matches), and solves the set by unification. A program whose branches disagree, or whose call has the wrong number of arguments, fails here.

WebAssembly code generation

The typed tree is lowered to WebAssembly, including the small standard library for printing and reading. The interpreter is the other consumer of that same tree: it evaluates expressions directly, with the standard library implemented in the host language.

The course requires that student implementations stay private, so the source is not on this site.
