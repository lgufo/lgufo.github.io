User-Space TCP Implementation

Fall 2025 · ELEC 3120 Computer Networks

Foggy TCP is the ELEC 3120 project, a TCP socket that runs in user space. An application sends and receives through the socket, and a backend thread carries each segment in a UDP datagram. The starter supplies that path, and its transfer is stop-and-wait. I measured delivery delay on it, replaced stop-and-wait with a sliding window, added fast retransmit and Reno, and finally switched congestion avoidance to TCP CUBIC. The course testbed is two virtual machines, a server at 10.0.1.1 and a client at 10.0.1.2, on a link of 100 Mbps with 20 ms of delay.

Measuring delivery delay

I measured how long a file takes to cross the link, from the client’s first write until the server has the whole file. The client writes the file into the socket, and the server stores what it reads.

The start time travels in the byte stream. Just before the first write, the client stamps the clock and prefixes the stamp to the data. The server removes it, writes the remaining bytes as the file, and stamps the clock again when the read returns empty. The printed difference is the delivery time. The server closes its socket only after that stamp. Socket creation and the client’s one-second wait sit before the start stamp. The client’s close is what makes the read return empty, so that signal falls inside the interval.

Sliding window

I replaced stop-and-wait with a sliding window, so several segments can be in flight. Stop-and-wait sent one segment and then waited for its acknowledgement.

The starter numbers the byte stream and breaks it into segments of at most one MSS. It acknowledges the next byte the receiver still expects, and that acknowledgement covers every earlier byte. The window holds every segment the acknowledgement has not yet covered. When the acknowledgement advances, the sender releases the covered prefix and the window slides forward. Stop-and-wait transmitted only the first segment in that window. I transmit every segment that has not yet been sent.

The starter delivered a segment only when it was exactly the next expected one, and it did not keep segments that arrived early. I store those in the 64 receive slots the starter allocated. Bytes reach the application only once they continue from the next expected offset. A segment that has already been delivered, or that is already in a slot, is dropped. The course fixes an MSS at 1,400 bytes minus the Foggy header.

Fast retransmit and Reno

I used fast retransmit for loss recovery. Three duplicate acknowledgements of the same next byte mean the segment at that sequence number was lost, and the sender retransmits it immediately. The stack has no retransmission timer, so a loss that never produces those three acknowledgements is not repaired.

I capped unacknowledged data by the smaller of the receiver’s advertised window and a congestion window. At this stage the congestion window follows Reno. The last stage replaces congestion avoidance and this loss decrease with TCP CUBIC.

The starter sets the window to one MSS and the slow-start threshold to 64 MSS. In slow start, each acknowledgement of new data adds one MSS, so the window roughly doubles over a round trip. At the threshold the sender enters congestion avoidance, where the window grows by about one MSS per round trip. On a loss the threshold falls to half the current window, the window becomes that threshold plus three MSS, and the sender enters fast recovery. The next acknowledgement of new data leaves recovery: the window returns to the threshold, and congestion avoidance continues.

The cap counts payload bytes sent but not yet acknowledged. Another segment goes out only when it still fits. The value it reads is the window the starter already advertises: the free space in a 65,535-byte buffer, or one MSS when less space remains.

TCP CUBIC

Reno opens the window by about one segment per round trip, which is slow on a wide pipe. For the last stage I kept the slow-start increase and fast retransmit, and switched congestion avoidance and the loss decrease to TCP CUBIC.

On a loss the sender saves the current window as Wmax and multiplies the window by β = 0.7. In congestion avoidance the target follows the time since the loss, rather than the number of round trips:

W(t) = C (t − K)³ + W_max
K    = ∛(W_max · β / C)

C is 0.4, and t is the time in seconds since the reduction. When the target is above the current window, each new acknowledgement moves the window toward it.

The slow-start threshold is set to this reduced window at the same time. During fast recovery, each further duplicate acknowledgement grows the window by one MSS, so the window can still advance while the loss is repaired. An acknowledgement of new data ends fast recovery: the window returns to the threshold, and congestion avoidance resumes. Each step toward the target grows the window by (W(t) − cwnd) · MSS / cwnd bytes, or by one byte when that increase would be smaller.
